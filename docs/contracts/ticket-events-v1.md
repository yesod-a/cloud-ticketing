# Ticket Events v1

This document defines the future ticket-service contract. It is intentionally runtime-free until payment and order event consumers are implemented and verified.

## Input and output topics

Ticket service consumes `PaymentSucceeded` from `ticket.order-events.v1` and publishes `TicketIssued` or `TicketIssueFailed` to the same order-event topic. Kafka keys remain `orderId`.

## Ticket issuance

For each order, ticket creation is idempotent on a unique `order_id` constraint. A retry of the same successful payment event returns the existing ticket and does not generate a second ticket code. The ticket record stores only a hash or encrypted representation of the code when plaintext disclosure is not required.

### `TicketIssued`

The payload includes `orderId`, `ticketId`, `ticketCode`, `issuedAt`, and the ordered seat references. `ticketCode` is generated by a cryptographically secure server-side generator and is never derived from a predictable database ID.

### `TicketIssueFailed`

The payload includes `orderId`, an idempotent `attemptId`, `reasonCode`, and a retryable flag. It must not expose stack traces or payment secrets.

## Recovery

- The consumer records `(eventId, consumerName)` before acknowledging the event.
- Transient failures are retried with bounded backoff through `ticket.retry-events.v1`.
- Events exceeding the retry budget are written to `ticket.dlq.v1` and surfaced for manual repair.
- A repair reruns issuance by `orderId`; the unique constraint and processed-event record make the operation safe to repeat.
- A paid order without a ticket is a reconciliation mismatch, not an automatic refund.

## Versioning

`schemaVersion=1` is additive-compatible. Breaking changes require a new topic version and a dual-read migration window.
